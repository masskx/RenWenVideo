# 配音（TTS）：阿里云百炼的模型、音色和用法

> 2026-10-16 整理。用户反馈：最近几部片子的配音很差，“一个词一个词地蹦”，模型也太基础。TTS 很便宜（3 分钟口播 ≈ 900 汉字，约 0.2–0.4 元），**不用为了省钱选差的**。来源都是阿里云帮助中心的官方页面（链接见各节），音色清单以官方页为准；实际调用都用本项目的 `DASHSCOPE_API_KEY` 试过（结果见第五节）。

## 〇、现行规定（2026-10-16 起）：所有视频都用用户自己的复刻音色（豆包语音）

用户在火山引擎“豆包语音”上传了自己的声音，做了声音复刻（2.0）。**以后所有视频的配音都用这个音色**，下面阿里云的内容降为备选（复刻音色不可用时才用）。

- 环境变量：`DOUBAO_API_KEY`（密钥，不要写进仓库、不要在对话里完整打印）、`DOUBAO_VOICE_ZH`（中文复刻音色 id，`S_` 开头）、`DOUBAO_VOICE_EN`（英文复刻音色 id）。
- 接口：`POST https://openspeech.bytedance.com/api/v3/tts/unidirectional`，请求头 `X-Api-Key`、`X-Api-Resource-Id: seed-icl-2.0`、`X-Api-Request-Id`（每次一个新 uuid）；请求体 `req_params.text / speaker / model: "seed-icl-2.0" / audio_params`。返回是一行一个 JSON 的流：`data` 是 base64 音频片段，最后一条 `code: 20000000` 表示成功。
- **逐字时间戳**：`audio_params.enable_subtitle: true`。每句返回一次 `sentence.words`（`word`、`startTime`、`endTime`，单位秒，整段连续的绝对时间）。所以和阿里云一样可以整段合成、卡点精确（已实测，公开音色上验证过）。
- 语速：豆包的 `audio_params.speech_rate` 是 -50…100（100 = 2 倍速）；脚本把配置里的 `rate`（1.0 = 正常）换算过去，`rate: 1.1` → `speech_rate: 10`。
- 配置（教程 JSON）：

```json
"tts": {"provider": "doubao", "rate": 1.1}
```

  不写 `voice` 就用 `DOUBAO_VOICE_ZH`；英文片子写 `"voiceEnv": "DOUBAO_VOICE_EN"`。需要换资源（比如公开音色）时写 `"resource": "seed-tts-2.0", "voice": "<公开音色 id>"`（`model` 只在复刻资源上发送）。

**当前状态（2026-10-16 实测，已可用）**：用户给 API Key 开通了声音复刻后，`DOUBAO_VOICE_ZH`（`S_XH4ScO592`）和 `DOUBAO_VOICE_EN`（`S_i4HBcO592`）都能正常合成，逐字时间戳正常，整条流水线（卡点、字幕）跑通。注意两点：

- **请求里不要带 `"model": "seed-icl-2.0"`**（官方示例里有这一行），服务端会报 `InvalidModel`；资源头 `X-Api-Resource-Id: seed-icl-2.0` 已经选好了模型。不带 `model`、或者带 `seed-tts-1.1` / `seed-tts-2.0-expressive` 都能出声；脚本默认不带。
- 计费按字符的资源是 `seed-icl-2.0`；`seed-icl-2.0-concurr`（按并发）返回“quota exceeded for types: concurrency”，没买就别用。
- 语速：用户的中文复刻音色在 `rate: 1.0` 时比之前阿里云 1.1 倍慢约三成（同一段 18 秒 → 23.6 秒）；英文复刻音色句中停顿较多（0.5–1.5 秒）。默认先用 `rate: 1.1`，用户听过样音后再定。
- 鉴权也支持应用的 APP ID + Access Token（环境变量 `DOUBAO_APP_ID`、`DOUBAO_ACCESS_TOKEN`，请求头 `X-Api-App-Id` + `X-Api-Access-Key`），设置了就优先用。

## 〇·二、语速随内容和情绪变化（用户规定，2026-10-16）

用的是用户自己的复刻声音，**节奏必须和画面的节奏对上**，所以语速不能全片一个数。规则：

1. **写口播时就定语速**，不是配完再调。分镜的镜头表加一列“语速”，每个镜头写一个档位和理由（比如“brisk：列举四个工具，跟着卡片一张张落下”）。
2. **按内容和情绪选档位**（为用户的复刻音色校准过：它在 1.0 时比普通 TTS 慢）：

| 档位 | rate | 用在哪里 |
|---|---|---|
| `slow` | 0.98 | 关键结论、转折、需要观众停一下的一句；结尾的提问 |
| `calm` | 1.04 | 解释原理、讲一个概念的来龙去脉；情绪克制的段落 |
| `normal` | 1.1 | 一般讲解（默认） |
| `brisk` | 1.18 | 开场钩子、过程演示、画面动作密集的段落 |
| `fast` | 1.26 | 列举（工具名、步骤名一个接一个）、快速回顾 |

3. **一个场景一个基调**：在 `tutorials/<id>.json` 的场景上写 `"pace": "brisk"`（也可以写数字）。场景里某一句需要换节奏时，在**这句开头**写 `{pace:slow}`，从这一句起换档；标记写在句中会自动挪到这句的开头——脚本只在句号处分段合成，不会把一句话切开（切开就会回到以前一截一截的问题）。
4. **和画面对节奏**：配完先看时间轴——快档位的段落，画面里的事件间隔要跟得上；慢档位的那句，画面要给出停顿（相机停住、主体回稳），不要在这句话上塞新东西。
5. 档位表可以在配置里覆盖：`"tts": {"provider": "doubao", "paces": {"brisk": 1.22}}`。全片只用一个档位时，`scripts/qa/brief.mjs` 会警告；用复刻音色而场景没写 `pace`、镜头表没有“语速”列，会直接不过。

## 一、为什么之前的配音一卡一卡的（最要紧）

不是只怪模型。`scripts/generate-tutorial-voice.py` 以前的做法是：**把每个场景按逗号、句号切成短句，每个短句单独请求一次 TTS，裁掉首尾静音，再按固定停顿拼起来**（为了让卡点时间精确）。结果每个短句都被当成一句完整的话来读：起调重来、句尾下沉、停顿长度一刀切——听起来就是一截一截往外蹦，整段话没有语气的走向。

**改法（已实现，`"segment": "scene"`，现在是默认）**：一个场景整段只发一次请求（WebSocket 流式接口），打开 `word_timestamp_enabled`，服务端按字返回时间戳，卡点和字幕时间直接从时间戳算。语气能跨句连贯，卡点照样精确到字。

- 旧做法保留为 `"segment": "phrase"`，只给已经发布的旧片子用，新片子不要用。
- 时间戳只在**流式**接口里返回（WebSocket，或 HTTP 的 SSE 模式），非流式 HTTP 不返回（[CosyVoice HTTP API](https://help.aliyun.com/zh/model-studio/cosyvoice-tts-http-api)、[服务端事件](https://help.aliyun.com/zh/model-studio/cosyvoice-server-events)）。脚本用 `dashscope` SDK 的 `tts_v2.SpeechSynthesizer`（`pip install dashscope`）。
- 服务端返回的 `begin_index` 不可靠（“，Web” 会算成一个字），脚本按返回的文字逐字对齐我们的口播文本，遇到读法被改写的字（“3” 读成“三”）照样一字一字往前走。

**长文讲解流水线还没改**（待办）：`scripts/build-explainer.mjs` 把每一行字幕单独合成一次（HTTP 非流式），还在每行末尾强行补一个句号，所以每行都按“一句话说完”的语调收尾，问题和旧的教程配音一样。改法：每个场景整段走 `synthesize_scene`（可以直接调用 `generate-tutorial-voice.py` 里的函数，或者照它的做法用 SDK），用逐字时间戳切出每一行的起止时间，再生成时间轴；配置里的 `voice.model` / `voice.voice` 换成第三节里的音色。下一部长文讲解开工前先做这件事。

## 四、怎么写配置

```json
"tts": {
  "provider": "dashscope",
  "model": "qwen-audio-3.1-tts-flash",
  "voice": "anmingyuan_v3.1",
  "rate": 1.1,
  "volume": 60,
  "instruction": "科技知识区短视频解说：语速稍快、吐字清楚、自然有起伏，像在给朋友讲一件有意思的事，不要播音腔。"
}
```

- `segment` 不写就是 `"scene"`（整段合成）。`rate` 0.5–2.0：短视频解说 1.05–1.15 比较顺；以前的 1.2 是为了弥补切句拼接的拖沓，整段合成后不需要那么快。
- `instruction` 只对支持指令的模型 / 音色生效（Qwen-Audio 3.x 全部；CosyVoice 只有复刻 / 设计音色和少数系统音色），≤100 字符（汉字算 2）。写**语气和场景**，不要写内容。
- 换模型、换音色、改语速或指令都会让旧的配音缓存失效，重跑 `npm run tutorial:voice -- <id>` 会重新合成。

**读音和数字**（整段合成后，这些问题更显眼，写口播时就处理）：

- 口播文本里用 `[显示|朗读]`：画面字幕显示左边，TTS 读右边。例：`[Web3|Web three]`（不写会读成“Web 三”）、`[0.81 秒|零点八一秒]`、`[GPT-4o|GPT 四 o]`。
- 多音字：换同音字写在“朗读”一侧（官方 FAQ 的建议），或者用 CosyVoice 的 `hot_fix`：`"params": {"hot_fix": {"pronunciation": [{"天气": "tian1 qi4"}]}}`。
- 英文缩写、型号、版本号：先在对比稿里听一遍；读得不对就用 `[显示|朗读]`。
- 停顿：靠标点。逗号是短停，句号是长停；需要更长的停顿就断成新的一句，不要堆省略号。SSML（`<break>` `<say-as>` `<phoneme>`）在 CosyVoice / Qwen-Audio 上都支持，但要整段包在 `<speak>` 里并在 `params` 里开 `enable_ssml`，目前脚本没用，需要时再加。

## 六、检查（出片前）

- 听整段配音，不看画面：有没有“一截一截”的感觉、句尾是不是每句都往下掉、数字和英文读对没有。
- `public/audio/tutorials/<id>/*.words.json` 里每个字都有时间；卡点 `{a}` 落在对应的字上（`node scripts/qa/marks.mjs` 的前后帧照常检查）。
- 响度仍由 `render-tutorial.mjs` 统一到 -15 LUFS；底乐 `musicVolume` 0.05–0.07，音效比人声低 12 dB 以上。
